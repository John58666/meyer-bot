2. Data model: que el bot nunca falle

Basado en Butterbase, Booking Chatbot Guide, CodeLink block approach, y Postgres exclusion constraints:

Las 3 tablas que importan (simplificado)
-- Reglas de disponibilidad (recurrente semanal)
availability_rules {
id uuid PK
professional_id uuid FK → professionals
weekday int -- 0=Dom, 1=Lun ... 6=Sáb
start_time time -- ej: "09:00"
end_time time -- ej: "18:00"
break_start time -- null si no hay descanso
break_end time -- null si no hay descanso
}
-- Bloqueos (excepciones puntuales)
time_blocks {
id uuid PK
professional_id uuid FK → professionals
date date -- día específico
start_time time -- ej: "10:00"
end_time time -- ej: "12:00"
reason text -- "Inventario", "Personal", etc
is_full_day boolean -- true = día cerrado completo
}
-- Booking del bot (solo referencia — existe en otra tabla)
bookings {
id uuid PK
professional_id uuid FK → professionals
starts_at timestamptz -- ⚠️ SIEMPRE UTC
ends_at timestamptz
status text -- pending|confirmed|cancelled
}

🔑 Principio: Availability is derived, not stored

El bot no consulta "slots disponibles" de una tabla. Calcula en el momento:

slots = availability_rules - time_blocks - bookings - past - min_advance

Esto hace que agregar un bloqueo en mi-horario inmediatamente afecte la disponibilidad del bot. Sin sync, sin webhooks, sin magia.

⏰ Timezone: store UTC, render local

availability_rules guarda hora local del profesional (ej: "09:00" sin timezone).
Al calcular slots: combina date + rule_time y convierte a UTC para comparar con bookings.

El bot siempre pregunta al backend. El backend conoce la timezone del profesional y hace la conversión.

🧱 Por qué bloques de 5 min (CodeLink approach)

Dividir el día en 288 bloques de 5 min permite:
• Calcular disponibilidad como operaciones numéricas, no comparación de strings
• Cachear resultados fácilmente
• Soportar cualquier duración de servicio (15, 30, 45, 60 min)
• Escalar sin degradación

Opcional: podemos empezar con el modelo simple de reglas + bookings e introducir blocks después si hay problemas de performance.

4. Cómo se conecta con el bot

Flujo completo: bloqueo en mi-horario → disponibilidad en bot
1
Admin/profesional crea bloqueo en el drawer del día
"Inventario — 10:00 a 12:00"
2
Backend inserta en time_blocks
Misma tabla, mismo store. Sin replicación.
3
Bot consulta disponibilidad vía API
GET /api/professionals/:id/availability?date=2026-02-07
4
Backend calcula slots disponibles
rules[weekday] = 09:00-18:00 | break 13:00-14:00
- time_blocks[10:00-12:00] | - bookings[15:00-16:00]
= slots disponibles: 09:00, 09:30, 12:00, 16:00, 16:30, 17:00
5
Bot presenta slots al cliente → cliente reserva
"Tengo disponible: 9:00, 9:30, 12:00. ¿Cuál prefieres?"

✅ Lo que garantiza que el bot no falle

  • Single source of truth: availability_rules + time_blocks + bookings son las únicas fuentes. No hay cache inconsistente.
  • Exclusion constraint en bookings (Postgres): dos bookings no pueden solaparse en el mismo profesional. Race condition imposible.
  • Min advance window: ej: no se puede reservar con menos de 2h de anticipación. Controlado por el backend, no por el frontend.
  • Buffer time: entre booking y booking hay X min de buffer. Configurable por servicio.
  • Full-day block: con is_full_day=true en time_blocks, el día entero se marca cerrado. Un solo insert.
